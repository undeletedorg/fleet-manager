# Fleet management

A Python standard-library command for inventory, SSH checks, CLI updates, service health reports, and coding-agent skill/instruction synchronization.

## Quick start

First run, from a fresh clone:

```sh
cp .env.example .env                       # fill in your domain and SSH user
cp examples/inventory.json inventory.json  # then edit for your hosts
./fleet validate
```

`.env` holds the identifying values — management domain, SSH user, service URLs.
`inventory.json` refers to them as `${FLEET_DOMAIN}` and friends, and a real
environment variable of the same name overrides the file. Anything left
undefined is named in the error rather than silently blank.

Then, from this directory; `./fleet` also works by absolute path from another directory.

```sh
./fleet validate
./fleet check --group coding
./fleet update --group coding --dry-run
./fleet update --group coding
./fleet services
./fleet service-update --group coding --dry-run
./fleet service-update --group coding
```

For skills and instructions, the shared collection starts empty. Audit and preview with:

```sh
./fleet skills check
./fleet instructions check
./fleet skills sync --dry-run
./fleet instructions sync --dry-run
```

See [skills and instruction management](docs/agent-content.md) for importing content, assigning it to agents, syncing, and handling conflicts. The source and assignments live in [agent-content/manifest.json](agent-content/manifest.json).

Requirements: Python 3.8+ and OpenSSH on the controller, Python 3.8+ on Linux targets, reachable management DNS/network, and existing SSH key access. Service checks additionally use the host's Docker Compose/curl or systemd tools. No Python packages need installing.

`check` discovers executables and reads installed versions. It does not determine whether a newer upstream release is available. `update` runs each installed tool's configured updater, then checks its version again. `update --dry-run` performs discovery and version checks and prints the exact proposed commands without executing updaters. Git is tracked but remains check-only because it is managed by Ubuntu packages.

`services` checks registered services. `service-update` updates the ones that declare an updater, then rechecks health: a service that is not healthy after its updater exits is reported as failed, not as a success. It refuses to run when the remote worker sits inside the target unit's own cgroup, because stopping such a unit kills the updater partway through. `update` never touches services, and `service-update` never touches the CLI tools. `--dry-run` prints the commands without running them.

By default tool commands target the `coding` group; `services` targets all hosts with registered services. Examples:

```sh
./fleet check --host workstation02 --tool grok
./fleet update --host workstation01 --tool claude --dry-run
./fleet check --group all
./fleet services --host workstation02
./fleet service-update --host workstation01
./fleet update --group coding --timeout 240 --jobs 3
```

`--host` and `--tool` are repeatable. A host filter intersects the group filter; use `--group all` to select an infrastructure host for a tool/connectivity check. `check --group all` checks SSH/Python availability on infrastructure hosts that have no CLI tools assigned. `services` only checks hosts with registered services.

Exit codes: `0` means every requested host/item passed, `1` means one or more operational checks failed, and `2` means invalid configuration, arguments, or a local error. An unchanged version after a successful updater is reported as `unchanged`, not as an independently verified latest release.

## What is tracked in git

The repository tracks the tool. The fleet's own data stays local, because it
names real hosts, users, and addresses:

| Ignored (yours) | Tracked stand-in |
| --- | --- |
| `.env` | `.env.example` |
| `inventory.json` | `examples/inventory.json` |
| `devices.md`, `coding-agents-cli.md` | `examples/devices.md`, `examples/coding-agents-cli.md` |
| `logs/` | `examples/logs/` |
| `docs/services/` (host runbooks) | — |

The files under `examples/` are generated by the same code that writes the real
ones, so they show the true output shape. Check `git status --ignored` before a
first push, and keep credentials out of everything tracked.

## Inventory and logs

`inventory.json` is the source of truth for hosts, groups, expected tools, executable candidates, updater arguments, and services. Keep credentials out of it; identifying values belong in `.env`.

These are created locally by the first run and are not in the repository — see [examples/](examples/) for what each looks like:

- `devices.md`: generated host inventory and service links.
- `coding-agents-cli.md`: generated tool methods, latest observations, and host attempts.
- `logs/`: immutable, dated JSON and Markdown run logs. JSON includes before/after versions, resolved executable paths, update commands, exit codes, and service details.
- `docs/services/*.md`: one runbook per registered service, written by you. A service's `runbook` field points at its path.

Tracked in the repository:

- [CLI operations](docs/cli-operations.md): detection, T3 Connect registration, failure handling, and repair guidance.

Every completed check/update/service run writes a log and regenerates the two inventory documents. `./fleet render` regenerates them without contacting hosts. A subset check preserves other tools' observations and original timestamps. Failed SSH attempts appear separately; they do not make older version observations look fresh. Keep dated JSON logs to retain observation history. `--no-render` suppresses document regeneration; `--log-dir PATH` selects a different log directory (use `--no-render` for experiments so experimental logs do not replace the normal inventory view).

`service_updaters` declares how a service is updated, in the same shape as `tools`: `paths` to locate the updater, `version_args` to read a version, and `update_args` to invoke it. A service opts in by naming one in its `updater` field; only `systemd_user` services can. Changing the update method — pinning an exact release, following a different channel — is an `update_args` edit in the inventory, not a code change.

Host `tool_overrides` can override a tool's `paths`, `version_args`, `update_args`, or installation note. For example, a different known installation path can be recorded for just one device. Paths must be absolute or start with `~/`; arguments are JSON arrays, never shell expressions. `path_dirs` defines the complete remote search PATH, including helper programs needed by updaters. When adding a host, review its actual installation method before assigning updater arguments.

## Execution behavior

SSH uses key-only authentication, connection and keepalive timeouts, no TTY, and strict host-key checking. Verify new host fingerprints through a trusted console before adding them to the controller's known_hosts. Existing SSH configuration still supplies keys, ports, aliases, and jump hosts. Checks do not install missing tools or change shell startup files.

Preferred executable paths are checked before PATH fallback. The report includes both the launcher and its resolved target, so a broken symlink or a different installation is visible. The remote environment is built explicitly rather than sourcing interactive shell profiles. Environment files and provider credentials are neither read nor copied by this command.

Hosts run concurrently (three by default); tools update sequentially on each host. Updaters run as the inventory SSH user without sudo. A per-user remote file lock prevents overlapping fleet update runs on that host. It does not coordinate with tools' own background auto-updaters. Per-command timeouts kill the updater process group; version checks are capped at 30 seconds. SSH transport loss may leave a remote worker completing its bounded operation: recheck state before retrying.

Raw updater stdout/stderr is intentionally not persisted because tools can emit private configuration. Reports retain failure classification and exit codes. Run the reported command over SSH when deeper diagnosis is necessary. A missing tool, failed version check, failed updater, and failed post-update verification are separate results. One failed tool does not prevent checks of the remaining tools or hosts.

## Verification

```sh
python3 -m unittest discover -s tests -v
./fleet validate
./fleet check --group coding
./fleet update --group coding --dry-run
./fleet services
./fleet service-update --group coding --dry-run
```

Tests use temporary fake executables and mocked transport; they never update fleet hosts. Live checks and dry runs verify discovery, service status, and command selection without upgrading software.
